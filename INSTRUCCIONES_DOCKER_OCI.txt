GUIA PARA DOCKERIZAR Y DESPLEGAR TECHMIND EN ORACLE CLOUD INFRASTRUCTURE (OCI)
================================================================================

1. ANALISIS DEL PROYECTO
------------------------

Proyecto: aplicación web Flask (app.py) que ofrece la interfaz en / y una API
POST en /api/contenido. Sirve HTML desde templates/ y CSS desde static/.

No utiliza base de datos ni variables de entorno obligatorias. requirements.txt
ya contiene Gunicorn, por lo que el contenedor debe arrancarse con Gunicorn, no
con "python app.py" (ese modo activa el servidor de desarrollo de Flask).

Los archivos models/modelo.joblib y models/vectorizador.joblib son opcionales:

- Si están dentro de la imagen, se usa el modelo TF-IDF entrenado.
- Si no existen, la aplicación sigue funcionando con el clasificador de reglas
  incluido en services/classifier.py.

El .gitignore actual excluye models/, por lo que los artefactos deben copiarse
de forma explícita al servidor o incluirse en el contexto de construcción si se
quiere desplegar el modelo entrenado. No subas el dataset original data/arxiv.csv
ni secretos a la imagen.


2. ARCHIVOS QUE SE DEBEN CREAR EN LA RAIZ DEL REPOSITORIO
---------------------------------------------------------

Crear el archivo Dockerfile con este contenido:

FROM python:3.13-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

RUN useradd --create-home --uid 10001 appuser && chown -R appuser:appuser /app
USER appuser

EXPOSE 8000

CMD ["gunicorn", "--bind", "0.0.0.0:8000", "--workers", "2", "--threads", "4", "--timeout", "120", "app:app"]

Crear el archivo .dockerignore con este contenido:

.git
.venv
venv
__pycache__
*.py[cod]
.ipynb_checkpoints
notebooks
reports
tests
data
.env
.DS_Store

Decisión para el modelo:

A) Despliegue ligero (fallback): deja "models" en .dockerignore o no lo
   copies al proyecto. La aplicación arrancará, pero sus predicciones serán
   las reglas de respaldo.

B) Despliegue con el modelo entrenado: ejecuta previamente
   "python train_model.py" y asegúrate de que existan:
   models/modelo.joblib
   models/vectorizador.joblib
   No añadas "models" a .dockerignore. Antes de construir, verifica que los
   artefactos se generaron con una versión compatible de scikit-learn. La imagen
   instala la versión más reciente permitida por requirements.txt; para máxima
   reproducibilidad, fija las versiones instaladas con "pip freeze" o con
   rangos exactos en requirements.txt antes de entrenar y construir.


3. VALIDACION LOCAL
-------------------

Desde la raíz del repositorio:

docker build -t techmind:1.0 .
docker run --rm -p 8000:8000 --name techmind techmind:1.0

En otra terminal, comprobar:

curl http://127.0.0.1:8000/
curl -X POST http://127.0.0.1:8000/api/contenido \
  -H "Content-Type: application/json" \
  -d '{"titulo":"Ciberseguridad","texto":"encryption and vulnerability scanning"}'

Detener con Ctrl+C. También ejecutar las pruebas de aplicación antes de enviar:

python -m unittest discover -s tests -v

La prueba debe hacerse dentro del entorno virtual (.venv) que tenga instaladas
las dependencias, o tras instalar requirements.txt.


4. PREPARAR LA INSTANCIA OCI
----------------------------

Esta guía asume una instancia Compute con Ubuntu LTS, IP pública y una cuenta
con acceso SSH mediante clave. Para una aplicación de demostración, una forma
VM.Standard.E2.1.Micro (x86) o una Ampere A1 (ARM) sirve; la imagen oficial
python:3.13-slim es multi-arquitectura. Construir directamente en la instancia
evita incompatibilidades entre arquitecturas.

En OCI Console:

1. Crea o selecciona una instancia Compute con IP pública.
2. Limita SSH/TCP 22 a tu IP pública (/32), nunca a todo Internet si es posible.
3. Crea una regla de ingreso TCP 80. Usa origen 0.0.0.0/0 solo si la aplicación
   debe ser pública. Para pruebas privadas, usa tu IP/32.
4. Para HTTPS posterior, crea también TCP 443. No abras el puerto interno 8000:
   Docker lo expondrá únicamente a través del puerto 80 del host.

OCI aplica reglas de red en el NSG o en la Security List de la subred. El
firewall del sistema operativo es una segunda capa y también debe permitir los
puertos que se publiquen.


5. INSTALAR DOCKER EN UBUNTU DE LA INSTANCIA
--------------------------------------------

Conéctate (sustituye IP_PUBLICA y la ruta de tu clave):

ssh -i /ruta/clave_privada ubuntu@IP_PUBLICA

Instala Docker y Compose Plugin:

sudo apt update
sudo apt install -y docker.io docker-compose-v2
sudo systemctl enable --now docker
sudo usermod -aG docker "$USER"
exit

Vuelve a conectarte por SSH para que el grupo docker tenga efecto y valida:

docker --version
docker compose version
docker run --rm hello-world

Si usas Oracle Linux en lugar de Ubuntu, instala Docker con el gestor dnf/yum
siguiendo el procedimiento de tu versión de sistema operativo y habilita el
servicio con "sudo systemctl enable --now docker". No mezcles los comandos apt
de esta sección con Oracle Linux.


6. COPIAR EL PROYECTO Y CONSTRUIR EN OCI
----------------------------------------

Opción recomendada: clonar un repositorio Git que contenga Dockerfile y
.dockerignore:

git clone URL_DEL_REPOSITORIO techmind
cd techmind
docker build -t techmind:1.0 .

Si el código no está en Git, desde tu equipo local puedes copiarlo por SCP:

scp -i /ruta/clave_privada -r /home/alejo/Documents/G9-LATAM-TEAM-76 \
  ubuntu@IP_PUBLICA:/home/ubuntu/techmind

En OCI:

cd /home/ubuntu/techmind
docker build -t techmind:1.0 .

Para entregar el modelo entrenado, comprueba antes de construir:

ls -lh models/modelo.joblib models/vectorizador.joblib


7. EJECUTAR COMO SERVICIO CON DOCKER COMPOSE
--------------------------------------------

Crear compose.yaml en la raíz con este contenido:

services:
  techmind:
    build: .
    image: techmind:1.0
    container_name: techmind
    restart: unless-stopped
    ports:
      - "80:8000"

Iniciar y verificar:

docker compose up -d --build
docker compose ps
docker compose logs --tail=100 techmind
curl http://127.0.0.1/

La aplicación quedará disponible en:

http://IP_PUBLICA/

Para probar la API desde tu equipo:

curl -X POST http://IP_PUBLICA/api/contenido \
  -H "Content-Type: application/json" \
  -d '{"titulo":"Spring Boot","texto":"Desarrollo de APIs REST en Java"}'


8. OPERACION Y ACTUALIZACIONES
------------------------------

Actualizar código/modelo:

cd /home/ubuntu/techmind
git pull                         # O volver a copiar los archivos mediante SCP
docker compose up -d --build
docker image prune -f            # Elimina solo imágenes colgantes

Diagnóstico:

docker compose logs -f techmind
docker compose exec techmind python -c "from app import app; print(app.url_map)"
curl -i http://127.0.0.1/

Si funciona en localhost pero no desde Internet, revisa, en este orden:

1. Que "docker compose ps" muestre el mapeo 0.0.0.0:80->8000/tcp.
2. La regla de ingreso TCP 80 en el NSG o Security List de OCI.
3. El firewall del SO (por ejemplo, "sudo ufw status" en Ubuntu).
4. Que la instancia tenga IP pública y ruta a Internet.

Para producción real, coloca un proxy inverso (Nginx o Caddy) delante del
contenedor, expón únicamente 80/443, configura un dominio y certificados TLS
con Let's Encrypt. No uses el puerto 8000 como interfaz pública permanente.


9. RESULTADO ESPERADO
---------------------

El único proceso público será Gunicorn dentro del contenedor. Docker reiniciará
la aplicación después de un reinicio de la instancia gracias a
"restart: unless-stopped" y al servicio Docker habilitado. No se requiere
volumen persistente mientras no se escriban datos en tiempo de ejecución.


10. ACTUALIZACION: ARQUITECTURA CON SPRING BOOT Y OBJECT STORAGE
----------------------------------------------------------------

Si Spring Boot es la interfaz gráfica y el punto de comunicación con el
usuario, esta es la arquitectura recomendada. No se debe fusionar Spring y
Flask en un único contenedor: son procesos y ciclos de despliegue distintos.

Internet -> Caddy/Nginx (puertos 80/443) -> Spring Boot (puerto interno 8080)
                                           -> Flask ML (puerto interno 8000)
                                           -> volumen /models (solo lectura)

El navegador solo conversa con Spring Boot. Spring invoca internamente la API
de Flask mediante la URL http://ml:8000/api/contenido. "ml" es el nombre del
servicio Docker, no una IP fija. Flask no debe publicar un puerto al host.

El modelo real de este proyecto son DOS archivos: modelo.joblib y
vectorizador.joblib. Se deben guardar versionados en un bucket privado de OCI
Object Storage; por ejemplo, en releases/v1/. Al iniciar o actualizar, se
descargan al disco de la VM en /opt/techmind/models y se montan en Flask como
un volumen de solo lectura. No son parte de la imagen Docker ni del repositorio.

Ejemplo de compose.yaml para sustituir al ejemplo sencillo de la sección 7:

services:
  proxy:
    image: caddy:2
    ports:
      - "80:80"
      - "443:443"
    depends_on:
      - spring
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config

  spring:
    image: REGION.ocir.io/NAMESPACE/hackathon-app/spring:VERSION
    environment:
      ML_API_BASE_URL: http://ml:8000
    expose:
      - "8080"
    depends_on:
      - ml

  ml:
    image: REGION.ocir.io/NAMESPACE/hackathon-app/ml:VERSION
    expose:
      - "8000"
    volumes:
      - /opt/techmind/models:/app/models:ro

volumes:
  caddy_data:
  caddy_config:

El Dockerfile de Spring debe construir su JAR y arrancar Spring Boot. El
Dockerfile Python indicado antes será el del servicio "ml". Se deben construir,
etiquetar y publicar dos imágenes distintas en OCI Container Registry.

Para que la VM lea el bucket privado sin guardar claves de OCI en ella, usar
Instance Principals: crear un Dynamic Group que incluya esta instancia y una
política de solo lectura para el bucket. Esquema Terraform de referencia:

resource "oci_objectstorage_bucket" "models" {
  compartment_id = var.compartment_ocid
  namespace      = data.oci_objectstorage_namespace.current.namespace
  name           = "techmind-models"
  access_type    = "NoPublicAccess"
}

resource "oci_identity_dynamic_group" "techmind_vm" {
  name          = "techmind-vm"
  description   = "VM autorizada a leer los modelos"
  matching_rule = "instance.id = '${oci_core_instance.hackathon_vm.id}'"
}

resource "oci_identity_policy" "read_models" {
  compartment_id = var.tenancy_ocid
  name           = "techmind-read-models"
  description    = "Lectura del bucket de modelos desde la VM"
  statements = [
    "Allow dynamic-group techmind-vm to read objects in compartment id ${var.compartment_ocid} where target.bucket.name = 'techmind-models'"
  ]
}

El mecanismo de arranque (cloud-init, systemd o script de despliegue) debe usar
la identidad de instancia para descargar ambos objetos antes de ejecutar
"docker compose up -d". No usar claves de usuario, archivos PEM ni URLs
preautenticadas permanentes dentro de los contenedores.

CORRECCIONES NECESARIAS EN EL TERRAFORM EXISTENTE
-------------------------------------------------

1. La security list hackathon_sl se crea, pero la subred no la asocia. Agregar
   esta línea dentro de oci_core_subnet.public_subnet:

   security_list_ids = [oci_core_security_list.hackathon_sl.id]

2. Limitar el ingreso TCP 22 a la IP administrativa en vez de 0.0.0.0/0.
   Mantener públicos solamente 80 y 443; no abrir 8080 ni 8000.

3. cloud-init instala Docker CE, pero no el plugin Compose requerido por la
   arquitectura anterior. También se debe comprobar que el usuario correcto de
   Oracle Linux sea "opc" y habilitar Docker antes de desplegar.

4. Se recomienda añadir outputs para la IP pública de la instancia y guardar
   el estado Terraform en un backend remoto seguro, no en un archivo local.

5. Nunca versionar terraform.tfvars, terraform.tfstate ni archivos .pem. Si
   una clave privada ya se compartió o subió a un repositorio, revocarla y crear
   otra inmediatamente.

DOMINIO Y HTTPS
---------------

El dominio se compra o se usa uno que ya poseas; OCI DNS no es registrador de
dominios. No necesitas el dominio para desarrollar ni para validar el despliegue:
primero prueba http://IP_PUBLICA. Cuando la aplicación funcione, crea una zona
DNS pública en OCI (o usa tu proveedor DNS), delega sus nameservers si aplica y
crea un registro A, por ejemplo app.tudominio.com -> IP pública de la VM.

Después configura Caddy o Nginx. Caddy puede solicitar y renovar certificados
Let's Encrypt automáticamente cuando el DNS ya apunte a la IP y 80/443 estén
abiertos. Entonces el acceso final será https://app.tudominio.com.


11. PREGUNTAS Y RESPUESTAS DEL DISEÑO
-------------------------------------

P: ¿Todo debe ir en un único Docker?
R: No. Un contenedor debe ejecutar una responsabilidad. La solución tiene, como
mínimo, tres contenedores: proxy inverso (Caddy/Nginx), Spring Boot y Flask ML.
Se conectan mediante la red privada que Docker Compose crea automáticamente.
Solo el proxy publica los puertos 80 y 443 de la VM.

P: ¿Cómo se conecta la interfaz Spring Boot con el modelo Python?
R: Spring Boot llama desde el servidor a Flask, no desde el navegador. Se define
la variable ML_API_BASE_URL=http://ml:8000 y Spring envía un POST a
/api/contenido. El servicio "ml" resuelve automáticamente al contenedor Flask
en Compose. No utilizar localhost, IP pública ni una IP fija para esta llamada.

P: ¿El modelo debe estar dentro de la imagen Docker?
R: No es lo recomendado. Guardar los artefactos versionados en Object Storage y
descargarlos en /opt/techmind/models durante el despliegue. Luego montar esa
ruta en el contenedor Flask como /app/models:ro. Esto permite actualizar el
modelo sin reconstruir la imagen de aplicación. Recuerda descargar los dos
artefactos: modelo.joblib y vectorizador.joblib.

P: ¿Cómo puede la VM leer Object Storage de forma segura?
R: Con Instance Principals: una Dynamic Group incluye la VM y una política IAM
le concede únicamente permiso de lectura sobre el bucket de modelos. Así no se
guardan claves OCI, archivos PEM ni secretos en las imágenes o contenedores.

P: ¿Cuándo debo configurar el dominio?
R: Después de que el despliegue funcione mediante http://IP_PUBLICA. El dominio
no es requisito para construir ni probar los contenedores. Una vez validado,
registrar o reutilizar el dominio, crear un registro A hacia la IP pública y
configurar HTTPS con Caddy/Nginx. OCI DNS aloja la zona DNS, pero no vende ni
registra dominios.

ORDEN FINAL DE IMPLEMENTACION
-----------------------------

1. Corregir Terraform: asociar la security list a la subred, restringir SSH y
   crear bucket, Dynamic Group y política de lectura de Object Storage.
2. Crear los Dockerfiles de Spring Boot y Flask, y construir dos imágenes.
3. Publicar ambas imágenes en OCI Container Registry.
4. Subir la versión validada de los dos artefactos del modelo al bucket privado.
5. En la VM, descargar los modelos con Instance Principals e iniciar Compose.
6. Validar interfaz y API por la IP pública.
7. Configurar dominio, registro DNS A, Caddy/Nginx y certificado TLS.

ADVERTENCIA DE SEGURIDAD
------------------------

No se deben versionar, copiar al contenedor ni compartir claves privadas,
terraform.tfvars o terraform.tfstate. Si una clave privada OCI se expuso fuera
del equipo o se subió a un repositorio, revocarla y generar otra de inmediato.
